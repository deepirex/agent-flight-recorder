Flight recorder · Do not open

Give every AI agent a flight recorder

"Trust me" has never been a control. Here's how I'd give AI agents real work without betting the company on a model's good behavior: hard rules, cheap independent judges, and a record no model can touch. Plus a working version you can run yourself.

DeepakOctober 202615 min readCode and demo on GitHub ↗
The short versionThe model does the thinking. Authority and evidence live outside it.

Every few months someone asks me whether a particular model is "safe enough" to let loose on production systems. I've stopped answering, because it's the wrong question. We don't let a brilliant new engineer push to main on day one either. Not because they can't be trusted, but because good systems don't depend on anyone being perfect.

AI agents are now doing real work: issuing refunds, merging code, emailing customers. Yet most of the trust we place in them still lives inside the model: its training, its refusals, its vendor's assurances. You can't audit that. You can't tune it to your own policies. And your security team can't plug into it.

Two people put words to this recently, and put them well. Satya Nadella argued that we need to separate the supply of intelligence from the authority over it, and to treat models, open or closed, as insider risks: not because they're malicious, but because any capable actor with access to important systems can make mistakes or be compromised. Nikesh Arora added the security view: nobody can show duty of care on top of a black box, and security teams need a stable way in instead of chasing every model release.

I agree with both. What follows is how I'd actually build it, and a small working version I put together to make sure I wasn't fooling myself.

What aviation already knew

Pilots are some of the best-trained professionals anywhere. Aviation still doesn't rely on that, and it's the safest way to travel largely because of it. The pilot works inside a system designed to hold when a very capable person has a bad day. Four parts of that system translate almost one to one.

The architecture

None of this will surprise anyone who has run a security program. It's identity, least privilege, separation of duties and logging, applied to a new kind of insider. The gateway at the center is what security people have called a reference monitor since the 1972 Anderson Report: always invoked, tamper-proof, and small enough to verify. The agent holds no standing privileges, every action is checked where it touches a real system, and whoever acts is never whoever approves or records.

What's new is a decision model acting as a referee. The big model does the thinking. A small, far cheaper model makes one narrow call on each proposed action: allow, escalate, or block. This sits on top of the model vendor's own safety training, not instead of it. The vendor keeps the universal floor. You own everything above it.

Reference monitor · Anderson, 1972Always invoked. Tamper-proof. Small enough to verify.

If you take one rule from this piece, make it this one: authority comes only from deterministic policy. The rules set the most an agent can ever do. The judges can only narrow that, never widen it. No model, the judges included, can approve something the rules don't already allow.

Four tiers, cheapest first

Each tier only sees what the one before it couldn't settle. Most actions are boring, and boring should clear in milliseconds.

T0Rules

Deterministic rules

Policy written as code (OPA or Cedar), secret scanning, diff-size limits, protected branches, spending caps, an allowlist of network destinations, tests that must pass. A rule can't be sweet-talked or prompt-injected.

This tier also owns anything involving arithmetic, counting or dates. Decision models are weak at those (TypeSafe's own documentation for Jev says to keep math in code), and honestly, so are most of us before coffee.

Cost: effectively zero · Latency: microseconds to milliseconds
T1Judge

Two judges on every consequential action

This is where a decision model like Jev from TypeSafe AI earns its keep. It doesn't write prose. You give it some state (the proposed action, the diff, the ticket that started the task) and a set of typed questions, and it returns one of the answers you defined, with a probability. Its three question types are Choice, Score and Noul (a yes/no probability).

That shape suits a referee. The output is closed and machine-readable, so every verdict can be logged, compared and audited, and the probability gives the router something to set thresholds on. A closed answer set doesn't make a judge right, though. It can still pick the wrong valid answer with great confidence, which is why it never works alone.

In a mature setup T1 runs two judges: the hosted model, and a local judge fine-tuned on your own decisions, from a different model family (more on that below). When they agree, routine actions clear quickly. When they disagree, that disagreement is itself the signal, and the action escalates.

# illustrative policy, not Jev's exact request format
state:     proposed action + diff + originating ticket
questions:
  intent    Choice  [matches ticket, exceeds ticket, unrelated]
  data_risk Score   [none, internal, customer PII, secrets]
  leak      Noul    "Output includes data about someone
                     other than the intended recipient"
route:
  both judges p(violation) < 0.05   → allow (reversible: verify after)
  either judge p(violation) > 0.80  → block
  judges disagree, or anything else   → escalate to T2
  # irreversible actions use stricter thresholds
  # judges can only restrict: nothing outside the T0 envelope is ever allowed

Thresholds are examples. Set yours from your own labeled incidents and re-measure calibration on your own data. Vendor calibration and speed figures are claims until you've checked them.

Cost: about $0.0001 per check · Latency: tens to hundreds of ms
T2Review

Escalation for the uncertain band

Anything the judges aren't sure about goes up a level: to a frontier model from a different vendor than the agent, or to a person for the high-stakes calls. The different vendor matters. Asking a model to grade its own family's homework goes about as well as you'd expect.

The router also sends a small random sample of approved actions for review. That's how you learn how often the cheap judge misses things, before an incident tells you.

Cost: expensive, used on a small slice of traffic · Latency: seconds, or a human queue
RECRecorder

The flight recorder

An append-only log of every step, flagged or not. Each entry carries the hash of the one before it, so deleting or editing an entry breaks the chain. Entries are signed and can be anchored in a transparency log such as Sigstore's Rekor.

Write it in the OpenTelemetry GenAI format, so it flows into the SIEM and the security tools you already run. That's the stable interface security teams have been asking for. It's also the evidence trail regulators now expect: Article 12 of the EU AI Act requires high-risk AI systems to record events automatically over their lifetime.

Each entry records which version of the policy, the rules and each judge made the call, plus the agent's reasoning trace where the provider exposes one. Reasoning traces are useful, but they're the model's account of itself, so the record never depends on them. It captures what was proposed, what was decided, by which control, and what actually ran. When something goes wrong, you can say exactly which control failed instead of holding a séance over the logs.

Cost: storage · The judge's verdict decides priority and retention, never whether a step gets recorded

What it costs

The first question any CFO asks about a referee on every step is the right one. Running a second frontier model over every action can cost almost as much as the agent itself. That doesn't survive a budget review, and it shouldn't. A decision model changes the math because it answers a narrow typed question instead of writing an essay.

Take an agent fleet making 10,000 actions a day, with about 2,000 tokens of state per check. That's 20 million judge tokens a day.

ApproachDailyMonthly
Frontier model judges every action at ~$3 per million input tokens, before output$60~$1,800
Jev judges every action at $0.042 per million input tokens, output free$0.84~$25
Tiered: Jev on everything, frontier review on 5% 3% escalated plus a 2% random audit sample$3.84~$115
<1%added to agent spend by the tiered referee in this example$0.0001per decision-model check

For scale, the agents in this example might spend 20,000 tokens of frontier reasoning per action, about $600 a day. The tiered referee adds well under 1% to that. Each Jev check costs about a hundredth of a cent.

Two costs matter more than tokens. Human review time, which is why the uncertain band has to stay narrow. And latency: TypeSafe quotes 70 to 500 ms per call, and early users report medians under 100 ms. That's fine in front of a push or a payment, and it's why reads and drafts aren't gated at all.

Figures are illustrative. Jev pricing is from TypeSafe as reported by InfoQ (October 2026). Frontier pricing varies by model and vendor. If the judge runs on your own hardware, the cost becomes a fixed GPU budget instead of a per-token fee.

Isolation, not secrecy

The model shouldn't be able to see or influence whatever evaluates it. Show a model its grader and it will learn to perform for the grader. Anyone who has managed a team to a metric has seen this film.

Design assumptionThe model knows it is monitored. Every control still has to hold.

But I don't rely on secrecy for that. Capable models can often tell when they're being tested, and a control that only works until the model guesses is security through obscurity with better branding. The design has to hold even when the model knows it's being watched, the way traders know their messages are monitored and the controls still work.

So the separation is structural:

  • The model has no channel to the judge. It never sees the questions, thresholds or verdicts.
  • The model never writes its own log. The harness records every step independently.
  • The judge reads structured fields (the tool call, its arguments, the diff), not free text the agent wrote for it. That shrinks the surface for prompt injection aimed at the judge.
  • Credentials live in the executor, scoped to each action, and expire. The agent never holds them.

A black box watching a black box?

This is the fair objection, and Satya raised it himself: models can and should check each other, but stack them carelessly and you get an opaque model, inside an opaque orchestration layer, watched by another opaque model. Turtles all the way down.

Restrict onlyJudges can block or escalate. They can never grant an action the rules don't already permit.

Here's why this design isn't that.

  • The judges aren't the trust anchor. Authority comes from deterministic rules, evidence from the recorder, and the final say on uncertain cases from people. A judge can only make the system more conservative. If every judge failed silently, the agent still couldn't do more than policy allows.
  • Their answers are closed and measurable. A decision model returns one of a fixed set of answers with a probability, so you can measure how often it's right against human decisions and how well its confidence matches reality. Try doing that with a free-text reviewer.
  • No model is checked only by its own family. The two judges come from different model families, T2 uses a different vendor, and disagreement escalates.
  • The evidence doesn't belong to any model. The harness writes the record. No model, agent or judge, controls the evidence used to evaluate it.

The judges are still models, and nobody can explain their weights. The design doesn't need to. It treats them the way it treats the agent: useful, measured, and never trusted with authority.

Own your judge

The flywheelEvery human decision in the recorder becomes a training label for the local judge.

A hosted decision model is the fastest way to start. The end state is a judge you train and run yourself. It's also the most practical answer I know to the point Nikesh made about guardrails reflecting each company's own values, rather than one global set owned by the model vendors. Three reasons:

  • Control. Sensitive actions are judged inside your network, and the judge learns what a violation means in your business, not a generic definition.
  • Independence. A judge from the same model family as the agent tends to share its blind spots, and AI-control research shows a monitor and the model it watches can end up coordinating. A judge from a different family, trained on your own decisions, makes those shared failures far less likely.
  • The data is already there. Every escalation and every human approval in the recorder is a labeled example. The system produces the training data for its own referee.
  1. Start off the shelf. A hosted judge like Jev, or an open-weight decision model such as d3-flash running locally if data can't leave your network.
  2. Collect. Keep every T2 and human decision as a labeled example.
  3. Fine-tune a local judge on those human-verified labels, from a different model family than your agents. Don't train it on labels a frontier model generated, or you copy that model's blind spots into your referee.
  4. Run both judges side by side. When they disagree, escalate. Two independent judges catch more than either one alone.
  5. Keep it honest. Hold out a red-team test set, re-check calibration after every agent model update, retrain on a schedule, and record which judge version made each decision.

A fine-tuned judge isn't free of bias. It carries the judgment of whoever labeled its training data. The difference is that those biases are yours to see, measure and fix, instead of sitting inside someone else's model.

Checking it against the principles

Satya laid out seven principles of observability. They make a good checklist, so here's where each one lives in this design.

PrincipleImplementation
Model diversityTwo judges from different model families, T2 from a different vendor than the agent. No model verifies its own work.
Observe everythingEvery step goes to an append-only, hash-chained, signed record in OpenTelemetry format, written by the harness. Outcomes can be reproduced without the model vouching for them.
VerifiabilityA random sample of approved actions goes to T2, a red-team test set is held out, and calibration is re-checked after every agent or judge update.
Independent controlsPolicy as code owned by the enterprise. Credentials live in the executor, scoped per action. The model sets none of it.
Independent auditabilityThe evidence is produced by the harness, not by any model, and is readable by the SIEM, auditors and regulators.
ContainmentA one-way boundary, no standing privileges, judges that can only restrict, and a human brake on the gateway.
Incident disclosureEach record names the policy, rule and judge versions behind every decision, so a disclosure can say exactly which control failed and what changed at runtime.

Where it can fail

Measured, not assumedRandom audit sampling turns the judges' miss rate into a number you can report.

Every control has failure modes. I'd rather list them here than have someone find them in production.

RiskMitigation
The cheap judge misses subtle sabotage from a stronger modelLayer it behind rules, escalate the uncertain band, and spot-check a random sample of approvals so the miss rate is measured rather than guessed.
Agent output contains text aimed at the judgeFeed the judge structured fields, keep instructions out of its state, and let rules veto regardless of what the judge says.
Too many escalations and approvers start rubber-stampingTune thresholds on real data, turn repeat decisions into policy, and track approval rates per reviewer.
Data can't leave your networkJev is a hosted API today with no published self-hosted option. For sensitive workloads, run an open-weight decision model such as d3-flash locally (as in my build below), or a guardian model such as Llama Guard, ShieldGemma or Granite Guardian, keep the same typed-question contract, and fine-tune it on your own decisions over time.
Latency on every stepGate only side effects. Reasoning, reads and drafts run freely and are logged; checks run where the agent touches the world.
The recorder itself becomes a sensitive data storeEncrypt it, redact secrets at write time, and give auditors read-only, scoped access.

Not a new idea. Finally a cheap one.

Safety researchers call this pattern trusted monitoring: a weaker model you trust watches a stronger one you don't. Redwood Research's AI Control paper tested it against a model actively trying to slip sabotage past the monitor, and found that monitoring plus a limited budget for human review held up far better than trusting the model. Open guardian models such as Llama Guard have been around since 2023, and agent frameworks have started screening tool calls before they run.

What's changed is that the parts are now cheap and standard enough to ship. Decision models make a per-step referee affordable. OpenTelemetry gives the record a shared format. Policy-as-code engines are mature. The missing piece isn't technology. It's deciding to put trust in the harness instead of the model.

I built a small one. Here's what happened.

SetupOne laptop. No network calls. About 1,200 lines of Python, Apache-2.0: deepirex/agent-flight-recorder.

Architecture diagrams are cheap, so I built a small version and ran it on my laptop. The agent is Gemma 4 12B, running through Ollama. The judge is d3-flash, an open-weight 9B decision model from the vLLM Semantic Router project. It speaks the same Choice, Yes/No and Score format as Jev, and it runs locally. Different model families, on purpose: Gemma from Google, d3-flash built on Qwen.

Every tool call goes through a gateway with the rules, the judge, a hold queue for humans, a snapshot of the sandboxed world before each consequential action, and a hash-chained, signed log. The world is simulated: git pushes go to a local repository, refunds to a ledger file, emails to an outbox folder, and no HTTP request ever leaves the machine.

I ran six scenarios twice. Once with a scripted red-team agent that deliberately proposes harmful actions, which is the standard way to test a monitor. Once with Gemma deciding for itself, at temperature 0 so the run can be reproduced. The live run is the interesting one. Nobody told Gemma to misbehave.

The code, every evidence run, and an unedited recording of a live run are on GitHub at deepirex/agent-flight-recorder. Each published record can be checked with a single command and no ML packages.

What I learned

  • Rules and judges catch different things. The rules stopped the secret and the protected-branch push without consulting any model. Only the judge caught the injected email and the unapproved promise, because both passed every rule.
  • The record is evidence. Each block produced an incident bundle: the full session up to that point, the snapshot taken before the action where there was one, and the files changed. Editing a verdict, deleting an entry, or editing and re-hashing an entry without the key were each caught at the exact entry.
  • The brake works. With it engaged, every action was refused and recorded, reads included.
  • Calibration is real work. My first live run held all four of Gemma's perfectly harmless confirmation emails (p 0.08 to 0.11) against a 0.05 threshold. Two fixes: the judge now gets the list of actions the gateway actually executed, built from the record rather than the agent's account; and the threshold moved to 0.10, with the reason written into the policy file.
  • A gap I hadn't designed for. After its emails were blocked, Gemma went browsing unrelated files, including the payments config with the key in it. Reads weren't gated, so nothing stopped it; the record caught it. Least privilege has to cover what an agent can read, not just what it can do.
  • Rules don't care about formatting. Denied once, the agent reformatted the key and config as JSON and tried again. Same content, same answer.
  • Latency is fine where it matters. A median of 1.7 seconds per decision with the judge running alone on a laptop, 3.2 seconds while it shared the GPU with the agent. The model card reports 19 ms on a datacenter GPU. In production the judge gets its own hardware.

Six scenarios aren't a benchmark, and I'd be suspicious of anyone who said otherwise. This version uses one judge rather than two, HMAC rather than public-key signatures, and runs the recorder in the same process as the harness. Each of those is a known step to production, listed in the proof-of-concept README. What it does show is that the architecture is buildable today, from open components, on one machine. It caught exactly the insider behavior we should worry about, and let ordinary work straight through.

Where I'd start

  1. Pick one agent with side effects. A coding agent that can push, or a support agent that can refund.
  2. Put a gateway in front of its tool calls. The agent proposes; the gateway executes with credentials the agent never holds.
  3. Turn on the recorder for everything, in OpenTelemetry format, hash-chained, sent to your existing SIEM.
  4. Write the T0 rules you already know you need: protected branches, spend caps, egress allowlist, secret scanning.
  5. Add a T1 judge to irreversible actions only, with a human queue for the uncertain band. Measure for two weeks, then widen.
  6. Start the labeling loop on day one. Every T2 decision is training data for the local judge you'll want within a quarter.

None of this needs a breakthrough. It needs someone to decide that trust belongs in the system, not the model, and then do the unglamorous work. If you're building something similar, I'd genuinely like to compare notes.
